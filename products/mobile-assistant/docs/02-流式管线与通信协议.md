# 02 · 流式管线与通信协议（Q7 / Q8 协议细节）

> 目标体验：**用户说完，2~3 秒内 Miru 开口**，而不是"说完 → 全量识别 → 全量生成 → 全量合成 → 才播放"。

## 1. 全链路时序（一条语音的完整旅程）

```
iPhone                      Miru Backend                       外部服务
  │ ①按住说话（或 VAD 自动）   │                                    │
  │──PCM 帧(每100ms,二进制)──▶│ VAD：检测说话开始/静音 500ms=断句    │
  │                          │ 积累缓冲区，每 800ms 跑一次部分识别   │
  │◀────stt_partial(文本)────│    └─ SenseVoice(本地,~200-500ms)   │
  │ ②松手 / VAD 判停          │                                    │
  │──audio_end(JSON)────────▶│ 最终识别 → stt_final                │
  │◀────stt_final────────────│                                    │
  │                          │ ③Pipeline: 组装 system+历史+user     │
  │                          │──stream 请求(附工具schema)──────────▶│ DeepSeek
  │                          │◀──delta: "今天有"─"三件事"─...───────│ (TTFT≈1.2s)
  │◀────llm_delta(文字)──────│  句级分块器：遇到"。"且≥8字 → 出句   │
  │                          │  ④TTS队列(预取1句)                  │
  │                          │──sentence(JSON)────────────────────▶│ MiniMax
  │◀──sentence + mp3帧───────│◀──SSE hex音频块─────────────────────│ (首包≈0.3-0.5s)
  │ ▶播放第一句（后续句边收边播）│                                    │
  │                          │  若 delta 变成 tool_calls：          │
  │◀────tool_start───────────│  执行工具 → 结果回填 → 再次 stream   │
  │◀────tool_end─────────────│  (工具执行期间手机上显示状态)         │
  │◀────turn_end(usage/cost)─│  落库 + 成本入账 + 后台记忆提取       │
```

**要点**：LLM 文本、TTS 音频、工具状态三条流在**同一条 WS** 上按发生顺序交错下发，手机端按事件类型分发给 UI 或播放器，天然保序。

## 2. 延迟预算

| 环节 | 预算 | 说明 |
|------|------|------|
| 说话结束 → 断句判定 | 500ms | VAD 尾静音阈值（可调） |
| 最终 ASR | 200-500ms | SenseVoice CPU；短句更快 |
| LLM 首 token（TTFT） | 1.2-1.5s | V4 Flash 实测 P50≈1.2s；**必须关 thinking**（否则先出推理，再等几秒） |
| 首句文本累积 | ≤800ms | 句级分块器早吐策略（见 §4） |
| TTS 首包 | 0.3-0.5s | speech-02-turbo 流式 |
| **合计：说完 → 开口** | **≈2.2-2.8s** | 行业标准语音助手水平 |

优化储备：DeepSeek 输出速度 ≈23 tok/s，正常回答一句 15-25 字，LLM 整句生成约 1-2s，与 TTS 播放速度（约 5 字/秒）持平 → **句子级流水线正好让"合成+播放"追着"生成"跑**，不需要等全文。

## 3. WS 协议定义（`/ws/session`）

### 3.1 帧约定

- **文本帧** = UTF-8 JSON，都有 `"type"` 字段
- **二进制帧** = 音频：上行固定为 **16kHz / 16bit / mono PCM**（约 32KB/s，每 100ms 一帧 = 3200 字节）；下行 TTS 音频格式在 `hello_ok` 里声明（默认 mp3，可选 pcm）

### 3.2 客户端 → 服务端

| type | 字段 | 说明 |
|------|------|------|
| `hello` | `token`, `device`, `persona`, `conversation_id?`, `mode: "text"\|"voice"` | 首帧；`conversation_id` 缺省则新建会话 |
| `text_input` | `text`, `attachment_ids?` | 文本要求与附件作为同一任务发送；只有附件而没有要求时不启动管线 |
| `audio_end` | `attachment_ids?` | 按键式说话：松手强制断句；语音要求与附件作为同一任务发送 |
| `interrupt` | — | 打断：停止当前 TTS 播放与 LLM 生成（barge-in） |
| `user_action` | `id`, `action: "confirm"\|"cancel"` | 高危工具确认（MVP2+） |
| `ping` | — | 心跳（服务端回 `pong`，30s 超时断连） |

上行二进制帧：语音模式下直接发 PCM；文本模式下忽略。

### 3.3 服务端 → 客户端

| type | 字段 | 语义 |
|------|------|------|
| `hello_ok` | `session_id`, `persona`, `tts: {format, sample_rate}` | 握手成功 |
| `stt_partial` | `text` | 部分识别结果（边说边显示，会被覆盖） |
| `stt_final` | `text`, `latency_ms` | 最终文本，进入 LLM 管线 |
| `user_text` | `text` | 确认收到的用户输入（文本模式直接发） |
| `llm_delta` | `text` | LLM 文本增量（手机显示流式字幕） |
| `sentence` | `text` | 一个完整句开始合成，**随后紧跟 1..n 个二进制帧**是该句音频 |
| `tool_start` | `id`, `name`, `args` | 工具开始执行（UI 显示"正在查群消息…"） |
| `tool_end` | `id`, `name`, `ok`, `summary`, `duration_ms` | 工具完成 |
| `turn_end` | `usage`, `cost_rmb` | 本轮结束（成本上报手机，用户可见） |
| `server_note` | `text`, `level` | 服务端提示（如"本月预算已用 90%"） |
| `error` | `code`, `message` | 本轮失败 |
| `pong` | — | 心跳应答 |

### 3.4 会话边界与重连

- 每轮对话 = `text_input`/`audio_end` 触发 → `turn_end`/`error` 结束；`turn_end` 前手机端忽略新的输入（或允许打断）。
- 手机断网重连：带 `conversation_id` 重新 `hello`，服务端从 SQLite 恢复历史，继续多轮。

## 4. 句级分块器（SentenceSplitter）——流式 TTS 的核心

LLM 输出的 token 流不能直接送 TTS（碎、无停顿），也不能等全文（慢）。规则：

```python
# core/splitter.py 的行为规范
- 缓冲字符；遇到边界符  。！？；… 或换行\n\n  且 缓冲长度 ≥ min_len(默认8字) → 出句
- 若缓冲 ≥ max_len(默认60字) 且无边界 → 强制按逗号/空格硬切
- 早吐策略：首句只要 ≥6 字且遇到边界就立刻出句（压低"开始说话"延迟）
- 定时器：距上次出句 1.2s 且缓冲 ≥8 字 → 出句（处理长句无标点）
- 流结束时 flush 残余缓冲
- 数字/英文句号不切（"3.14"、"U.S."）——只在边界符后跟中文或空格时才切
```

英文句点 `.` **不作为**边界符（避免切碎 URL/小数），英文句子靠 `\n` 与长度兜底。

## 5. TTS 队列与预取

```python
# tts/queue.py 的行为规范
- asyncio.Queue 保序；worker 逐句调 TTS provider，发 sentence 事件 + 音频二进制帧
- 预取 1 句：worker 在合成第 N 句时，同时启动第 N+1 句合成（并发上限 2），
  手机播完第 N 句时第 N+1 句已就绪 → 句间零等待
- 合成失败（网络抖动）：该句重试 1 次 → 失败则自动切 edge-tts 兜底重试 → 
  再失败发 error("tts_unavailable")，但文字已全部下发，用户不丢信息
- 打断（interrupt）：清空 TTS 队列与播放器，立刻进入新用户输入处理
```

## 6. VAD 断句（stt/vad.py）

MVP 用**能量法**（零依赖、可调参、够用），后续可换 Silero ONNX：

- 16kHz 帧 → RMS 能量；自适应噪声底（前 500ms 校准）→ 阈值 = 底 + 6dB
- 连续 ≥300ms 高于阈值 = 说话开始；连续 ≥500ms 低于阈值 = 断句
- 上限 15s 强制断句（防长按）；下限 300ms 忽略（防误触）
- Silero VAD（sherpa-onnx 附带模型）作为 `vad.engine=silero` 可选项，换引擎不改上层接口

## 7. 降级矩阵（任何组件挂掉都不全挂）

| 故障 | 降级行为 |
|------|----------|
| STT 模型未下载/失败 | 文本模式照常；语音请求返回 `error(stt_unavailable)` 并提示 |
| DeepSeek 超时/限流 | 重试 2 次（5s/30s）→ `error(llm_unavailable)`；不丢对话历史 |
| MiniMax 失败 | 该句切 edge-tts；连 edge-tts 也失败 → 只出文字不出声 |
| 微信工具异常 | 该次工具返回错误摘要给 LLM，让 Miru 用自然语言解释"现在读不到微信数据" |
| 成本账本写入失败 | 仅告警日志，不影响对话 |

## 8. 为什么不用"全量→全量→全量"

```
传统: 录音 ▸ 完整STT ▸ 完整LLM ▸ 完整TTS ▸ 播放       总延迟 8-15s，用户早已走神
本方案: 录音 ▸(500ms) STT ▸(1.2s) LLM流 ▸(0.5s) 首句TTS ▸ 边生成边播放
```

句级流水线在"响应感"上等价于真·逐 token 合成（人耳无法分辨 1 句内的差异），但工程复杂度低一个数量级——这是本方案最重要的一个务实取舍。
